# 008. 「メレを読む」を新設し、保護期間中の曲は本体を暗号化して公開サイトに置く

- 日付: 2026-09-18
- 対象: `/mele`・`/mele/:id`（`src/pages/MeleListPage.tsx`・`MelePage.tsx`）、`src/mele/`、`src/content/mele.ts`、`content/mele/`、`src/content/mele-locked/`、`src/content/mele-keyinfo.json`、`scripts/mele-lock.ts`、`docs/DESIGN.md`「歌詞（mele）引用の規約」（003 を一部改める）

## 決定

1曲ごとのページで、歌詞を1行ずつ「ハワイ語・全語の逐語の意味・行の訳・文法メモ（ʻŌlelo Hawaiʻi 講座の該当レッスンへのリンク）」で読めるようにする。曲は2つに分ける。

| 区分 | 条件 | 本体の置き場所 |
|---|---|---|
| 公開（public） | 003 の条件（作詞者全員が1967年末までに死亡、かつ1929年より前に出版） | `content/mele/<id>.ts` に平文 |
| 鍵付き（locked） | それ以外 | 平文は Drive の `ao-hawaii-private/mele/<id>.json`。`npm run mele:lock` が手元で暗号化し、暗号文だけを `src/content/mele-locked/<id>.json` に置く |

題・作者・成立の背景・関連レッスンは、どちらの区分でも公開する（歌詞を引かない部分）。

暗号化の方式:

- パスフレーズから PBKDF2-SHA256（600,000回）で鍵を導き、AES-GCM 256bit で暗号化する。salt はサイト共通で `src/content/mele-keyinfo.json`、IV は暗号化ごとにランダム。曲の id を追加認証データに入れ、暗号文を別の曲のファイルへ移しても復号できないようにする
- パスフレーズは `mele:lock --init` が生成して Drive の `passphrase.txt` へ直接書く。画面・会話・Worklog・引き継ぎ書には出さない
- ブラウザは、復号に成功した鍵を IndexedDB に `extractable: false` の CryptoKey として保存し、以後その端末では入力を求めない。「この端末から鍵を消す」で消せる
- 保護曲の平文は CI から見えないので、`mele:lock` が暗号化の前に公開曲と同じ検査（`src/mele/validate.ts`）をかけ、通らなければ書かない

## 背景

サイトの持ち主（フラ歴18年）の指摘。「著作権が切れている曲はかなり古く、最近の潮流と合っていない。読んでも実際のフラに活かせないので、最近の曲も載せたい」。003 の規約のままでは、踊っている曲の大半は1〜2行の引用しか置けない。

持ち主は、自分しか使わないので著作権のある曲も載せられないかと尋ねた。GitHub Pages は公開で、リポジトリも public なので、平文で置けば見る人が本人だけでも公衆送信になる。そこで次の3案を示し、持ち主が暗号化を選んだ。

**法的な前提は断定しない。** 本人しか中身を読めないので「公衆に向けて送信している」とは言いにくい、というのが本サイトの前提で、判例で確かめたものではない。持ち主がこのリスクを受け入れて選んだ方式である。歌詞の書き起こしは、持ち主が所有する歌詞カード・曲集の写真から行う（私的使用のための複製）。

## 比較した代替案

| 案 | 却下理由 |
|---|---|
| 保護曲は手元の dev サーバーでだけ表示する | 持ち主が「手元でしか見られないのは手間」と却下。稽古の前後にスマホで読めない |
| Cloudflare Pages ＋ Cloudflare Access のログイン付き別サイト | 閉じ方はサーバー側で確実だが、アカウント作成と2サイトの運用が要る。持ち主が暗号化を選んだ |
| 歌詞は載せない（PD の曲だけ全文、ほかは短い引用） | 行ごとの逐語注が付けられず、「最近の曲をフラに活かす」目的を満たさない |
| 暗号化を CI（GitHub Actions の secret）で行う | 平文を CI へ渡す private な置き場所が別に要る。手元で暗号化すれば平文は持ち主のマシンと Drive から出ない |
| 曲ごとに別のパスワード・別の salt | 端末ごとに曲の数だけ入力が要る。1つの鍵で全曲を開ければ足りる |
| 導いた鍵を localStorage に保存 | 鍵を文字列に書き出す必要があり、鍵そのものを持ち出せる。Pages のオリジン `iiiitiiitiiti.github.io` は持ち主の他リポジトリのサイト（flashcards・instrument-lessons など）と共有している |
| 歌詞本体を MDX で書く | 語と逐語注の対応（語を並べると行になるか）を機械で検査できない |

## 影響

- IndexedDB の鍵も同じオリジンの JS からは使える。鍵の中身は取り出せないが、他リポジトリのサイトのスクリプトが `indexedDB.open("ao-hawaii-mele")` で鍵を取り、公開されている暗号文を復号することはできる。持ち主の他サイトが改ざんされた場合に限られるので、受け入れたリスクとする
- 書き起こした歌詞の全文は、書き起こしを行った Claude のセッションログ（`~/.claude/projects/**/*.jsonl`）に残る。避けられないので、ここに記録しておく
- テスト（`tests/mele.test.ts`）は、保護曲について平文の `content/mele/<id>.ts` が無いこと、暗号文ファイルが `{v, iv, ct}` だけであることを検査する。平文の中身は CI では検査できない（`mele:lock` の検査に任せる）
- 暗号化の往復テストは、実在の歌詞ではなくダミーの歌詞で行う
- パスフレーズを作り直すと、既存の暗号文は読めなくなる。そのときは Drive の平文から `mele:lock` で全曲を暗号化し直す
- ウクレレ教材（instrument-lessons）へ同じ仕組みを入れるのは別の設計にする。曲データがメロディ（ABC）とコードも持ち、最近の曲ではそれも著作物なので、鍵をかける範囲と権利の記録（`docs/songs-licensing.md`）の扱いが変わる
