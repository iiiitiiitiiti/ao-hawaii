# 015. 画面を丸ごと描く総当たりテストは、組ごとに分ける

- 日付: 2026-09-24
- 対象: `tests/melePages.test.tsx`（曲が関連に挙げたレッスンから戻れるかの検査）、今後 `AppRoutes` を描いて総当たりするテスト全般

## 決定

全曲×関連レッスンを1つのテストの中のループで描いていたのを、`test.each` で「曲×レッスン」の組ごとのテストに分けた。1件は最長でも数十ミリ秒で終わり、曲やレッスンが増えても1件あたりの時間は増えない。`testTimeout` は既定の 5000ms のまま変えない。

## 背景

Windows は jsdom の生成が遅く（実行時間の50〜73%）、この1テストだけが既定の 5000ms を超えて落ちていた（2026-09-24 に Windows で実測）。Mac では全件通っていた。テストの中身とリポジトリの状態は正しく、失敗の原因は時間だけだった。

## 比較した代替案

| 案 | 却下理由 |
|---|---|
| vitest の `testTimeout` を 20000 程度に上げる | 曲が増えるたびに1テストの時間が伸び、いずれまた超える。ほかのテストの本物の固まりも見逃しやすくなる |
| Windows では落ちたままにして記録だけ残す | 両 OS で開発するため、Windows の `npm test` が常に赤いと本物の失敗に気づけない |

## 影響範囲

- `AppRoutes` を描いて全件を回すテストを新しく書くときは、同じく組ごとに分ける
- テスト件数の表示が増える（2026-09-24 時点で 29 files / 541 tests）

## 検証

Mac で `npm test` が全件通り、分けたテストの1件は最長 21ms だった。Windows での再実行は引き継ぎ書 `windows-tasks-2026-09-24.md` のタスク5に書いた。Windows で分けたテストがまた時間切れになれば、この判断を見直す。
